# Сверка намерения чтения с записью наблюдения

На R3 удаление активной записи `PENDING` или её замена предыдущей `EMPTY` с теми же смещением и записью приёма возвращали ложное `EVIDENCE_READY` после потери уже полученного своевременного пакета. Отдельно воспроизведён один обычный `getUpdates` после появления остановки наблюдателя между записью намерения и вызовом.

R4 сохраняет номер поколения и SHA-256 активной записи в существующей записи наблюдения. Поколение увеличивается при каждом обычном чтении, включая последовательные пустые ответы на том же смещении. Вызов возможен после обеих устойчивых записей. При пропаже активной записи, её замене или остановке между записями наблюдатель фиксирует неопределённый исход до сетевых запросов. Если точный пакет уже сохранился, он остаётся доступен для локальной оценки.

После записи намерения тестер повторно сверяет курсор и проверяет действующие ограничения, включая остановку и паузу. При известном отказе до API фиксирует `NOT_DISPATCHED`. Допуск к вызову использует меньший из свежего бюджета и исходного остатка. Проверка с исходным бюджетом 3 с, затратой 2 с на записи и свежим допуском 9 с передала API ровно 1 с.

## Проверка без сети

Команда для запуска из корня Friday_rework.

```bash
(
  set -e
  checkpoint=docs/checkpoints/2026-11-07-v3-original-context-repair
  draft="$checkpoint/drafts/baseline-ordinary-batch-capture-20261120"
  candidate_dir=$(mktemp -d)
  trap 'rm -r -- "$candidate_dir"' EXIT
  source="$checkpoint/evidence/tester/bot_tester.installed.py"
  verify_sha() { printf '%s  %s\n' "$1" "$2" | sha256sum -c -; }
  verify_sha cc36c0933bd01cfa5c33a3fb1123fefd0345a2185fbcf7f70f5a3bc2f7c0905b "$source"
  cp "$source" "$candidate_dir/bot_tester.py"
  patch --batch --forward --fuzz=0 -d "$candidate_dir" -p1 < "$draft/ordinary-batch-capture.patch"
  cp "$candidate_dir/bot_tester.py" "$candidate_dir/bot_tester_r1.py"
  verify_sha 002fdbcada5e3cb4c516e01807177a2cbb573f439f24a2491e370d611c48b4af "$candidate_dir/bot_tester_r1.py"
  patch --batch --forward --fuzz=0 -d "$candidate_dir" -p1 < "$draft/r2/ordinary-poll-witness.patch"
  cp "$candidate_dir/bot_tester.py" "$candidate_dir/bot_tester_r2.py"
  verify_sha 2a328fb6763e638bc297502945b24aa595a1a76a54da21e06898912e098ceed2 "$candidate_dir/bot_tester_r2.py"
  patch --batch --forward --fuzz=0 -d "$candidate_dir" -p1 < "$draft/r3/ordinary-poll-intent.patch"
  cp "$candidate_dir/bot_tester.py" "$candidate_dir/bot_tester_r3.py"
  verify_sha b2ff1b299d88531e9ac7d3573279a0c0a54810fc1d5e928713aba39514703bd6 "$candidate_dir/bot_tester_r3.py"
  patch --batch --forward --fuzz=0 -d "$candidate_dir" -p1 < "$draft/r4/ordinary-poll-pin.patch"
  verify_sha ac1b13a1e3868098e39c8df7a6592da7a5c5d8765e8a0b8fedfc9167c57e8f7f "$candidate_dir/bot_tester.py"
  python3 -I -B "$draft/r4/check_pin.py" "$candidate_dir/bot_tester.py" \
    "$candidate_dir/bot_tester_r3.py" "$candidate_dir/bot_tester_r2.py" "$candidate_dir/bot_tester_r1.py"

```

Прошли 43 проверки. Использованы временный журнал, синтетический транспорт и управляемые часы. Проверены удаление и подмена намерения, остановка перед вызовом, обе точки расхождения записей, три обычных пустых чтения на одном смещении и возобновление после подтверждённого пустого ответа. Квитанции ранних версий проверяются без изменений. Действующий тестер, длительность проверок на его защищённом состоянии и Telegram в этом запуске не затронуты.

## Привязка одного обычного запуска

[`ordinary_admission_source.py`](ordinary_admission_source.py) компилирует один отдельно выданный допуск в точный R4 с читателями истории (`44577894f0669d305d2cd713048928c7ccbce265a40f1f6d09080b1fb62228bd`). Использует те же точки привязки, что F07 и WORD2247. Сверяет SHA сценария, размер и SHA канонического допуска, выбранный run ID, ссылки на проверяющий, текущее доказательство, контракт и подготовку. В скомпонованной копии ветки командной строки закрыты. Начальный `Runner.new`, штатные `send` и `observe` остаются входами существующего одноразового вызывающего процесса.

Исходный тестер выполняет прежние проверки истории, предшественника, времени, boot и gateway. Скомпонованный проверяющий подтверждает факты на `NEW`, `CURSOR_AUTHORITY` и `PRE_INTENT_REVALIDATION`. Его точные байты заново сверяются на каждой границе. Выдающий допуск и процесс с текущими блокировками и часами ещё нужно привязать к будущему запуску.

До запуска часов `qualify_selected_ordinary_readonly` передаёт отдельный этап `READONLY`. Он проверяет SHA сценария и исполняет штатный префикс `Runner.new` до построения строки. Для вложения сохраняются исходный читатель и проверки остановки. Вызов требует `api=None`. Доказательство `preclock` допускает только `READONLY`, при котором часы операции и запись вызова ещё отсутствуют.

[`ordinary_current.py`](ordinary_current.py) проверяет конкретные часы, родительский слот, блокировки потребителя, ту же власть, текущий курсор и состав строк. Старая история по-прежнему проверяется самим R4. В `NEW` собственной строки ещё нет. На двух этапах отправки она должна быть точной `PREPARED` с нулём попыток и исходным смещением. После устойчивой записи намерения тот же внешний monotonic-срок проверяется ещё раз прямо перед API. На отказе после записи R4 сохраняет `PRE_REQUEST_REFUSED`. Штатные ACK10 и окно180 не меняются, обслуживание оставляет 5 секунд, запуск ограничен 300 секундами внутри внешних 600.

[`check_ordinary_admission_source.py`](check_ordinary_admission_source.py) запускается через `python3 -I -S -B` с точным скомпонованным R4 и сохранённым пассивным сценарием. На точных входах S01 и D10 по 23 изолированных теста. Новый проверяющий работает под настоящими временными блокировками родителя и потребителя, с инертным наблюдателем прав и транспортом в памяти. После изменения прав во время третьего GET остаются точная `PREPARED` и ноль попыток. После истечения внешнего остатка за границей записи намерения POST отсутствует. Положительный имитационный ACK10 сохраняет окно180 и читается прежним R4.

На Core295 [наблюдатель текущей области](ordinary_core295_scope.py) проверил точную личную беседу S01 и её сохранённый маршрут, действующую политику `read_file`, доступные каталоги профиля и выбранный файл pairing. Использованы существующий локальный протокол и два целевых запроса SQLite в режиме `mode=ro` с `query_only`. Финальная проверка штатным `qualify_before_clock` под тремя блокировками сохранила 548 записей и курсор. Часы, активный одноразовый вызов и отправка отсутствовали. Для живого исполнения остаётся штатный вызывающий процесс, который связывает текущие решения владельца и короткоживущее доказательство с исходными часами. Путь открытого работающим процессом PairingStore и авторизация конкретного будущего события проверяются на ближайших действующих границах. Для S14 [проверяющий полученной пары](s14_pair_receipts.py) после штатной проверки R4 принимает защищённую связь исходного ACK и нативного входа. Он сверяет обе квитанции по роли, имени, SHA и длине, учитывает разные ID на двух концах. До реальной попытки остаётся подтвердить остановку до второго вызова транспорта. Принятый план фиксирует два самостоятельных файла TXT и PDF.
